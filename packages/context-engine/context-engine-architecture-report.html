Context Engine Report

ContextGo 长期上下文引擎架构约束报告

这份报告把当前讨论固化成一个清晰的长期方向：ContextGo 的核心不是把聊天历史做长，也不是把工作目录做成渐进式披露的文件树，而是以 Space 为逻辑边界，构建一个可形成、可演化、可治理、可协作的 Context Engine。

判断基线

  • context window 是执行窗口，不是记忆本体。
  • RAG 只覆盖 retrieval 的一部分，不是完整记忆系统。
  • 工作目录只能提供 runtime material，不能承担长期上下文主身份。
  • Space 必须高于 Conversation、Thread、Mount 和单次执行。

设计来源

  • 论文综述提供 forms × functions × dynamics 的问题空间。
  • Supermemory 提供 memory engine / context service 的建模参考。
  • AFFiNE 提供 local-first、doc/canvas 和协作表面的能力参考。
  • ContextGo 当前产品已具备 agent、connector、IM 和 runtime 壳层基础。
核心结论 参考资料 文档地图 五层架构 治理边界 对象模型 记忆生命周期 Runtime 与 Connector AFFiNE 吸收 实施路线

1. 核心结论

ContextGo 下一阶段不应继续围绕“单个工作目录下的 agent 协作”做线性扩展，而应把已有的 agent runtime、connector、IM channel、automation 能力上提到 Space-first 的结构中，由一个独立的 Context Engine 负责长期上下文沉淀与每次执行的 Context Pack 组装。

Space 是长期逻辑空间，Context Engine 是空间之下的记忆与上下文子系统，Context Pack 是一次执行真正送进模型窗口的可解释载荷。

必须避免的偏差

  • 把 Space 退化成“某个目录的高级名字”。
  • 把 Conversation 当成长期知识容器继续膨胀。
  • 把 connector 只当成“导入文本到 prompt”的桥。
  • 把图谱、白板、笔记 UI 误认成 context engine 本身。

必须固定的判断

  • 记忆系统必须分层，不同层使用不同索引结构。
  • 记忆必须具备 formation、promotion、compaction、forgetting、review。
  • 高价值记忆要有 provenance、scope 和人机协作介入点。
  • Space、Thread、Mount、Context Pack 必须语义稳定，不再漂移。

核心翻译 1：为什么记忆不能等于 RAG

论文的核心意思可以翻成一句更工程化的话：Agent 的记忆不是简单把外部文本检索回来，它是一套让系统能形成状态、积累经验、保留工作上下文，并在之后任务里被有选择地取回和更新的机制。

核心翻译 2：三维框架

  • Forms：记忆以什么形式存在，例如 token-level、parametric、latent。
  • Functions：记忆承担什么作用，例如 factual、experiential、working。
  • Dynamics：记忆如何在时间中运行，例如 formation、evolution、retrieval。

核心翻译 3：对 ContextGo 的直接启发

  • Context window 只是视窗，真正的系统核心是记忆对象和生命周期。
  • Context Pack 不能等于历史拼接，而是 task-scoped 的筛选和装配。
  • 长期上下文必须拥有升级、压缩、遗忘、审批和 provenance 机制。
  • 文件树、知识图、白板都只是表面或证据层，不能直接等于记忆引擎。

3. 五层总架构

整体系统建议拆成五层，每层解决不同问题。上层偏产品心智和人机协作，下层偏长期上下文治理和执行编排，中间通过稳定对象模型衔接。

Layer 1 · Space Layer 顶层产品逻辑空间。负责 spaceId、成员、权限、默认边界、协作归属、长期资产组织。
Layer 2 · Execution Layer Thread / Conversation / Agent Run / IM Session / Cron / Hooks / Runtime Workspace。负责任务执行，不定义长期记忆。
Layer 3 · Ingestion Layer 统一吸纳 connector、工作目录文件、IM 消息、用户编辑、Agent 产物，把它们转换成标准化上下文对象。
Layer 4 · Context Engine Layer document -> chunk -> memory -> profile -> retrieval -> context pack。这是长期记忆、生命周期和装配中枢。
Layer 5 · Human Surface Layer Space Docs / Space Canvas / Members / Memory Review / Context Graph。负责让人理解、编辑、审批和协作。

5. 长期治理边界

这套约束不是“等以后实现多了再统一”的文档，而是现在就应该启动的一轮治理。因为项目已经同时拥有 Agent runtime、Space、Context Engine、Connector、IM channel、Docs/Canvas 这些高耦合方向，如果不尽早固定边界，后续每新增一个能力都会把系统再拉向不同的心智模型。

当前最需要防止的不是“功能不够多”，而是“多条能力线各自沿着自己的术语和边界发展”，最后把产品拖进不可维护的多中心架构。

必须被治理的五个边界

  • Space vs Conversation：顶层主语必须是 Space，不是会话。
  • Context Engine vs Surface：文档、白板、图谱是表面，不是引擎。
  • Context Engine vs Runtime：记忆与装配属于引擎，执行循环属于 runtime。
  • Connector Repo vs Product：独立 connector 项目负责接入控制面，主产品负责产品化吸收。
  • Human Governance vs Auto Loop：审批、权限、审计不能藏进 runtime 私有协议里。

如果不治理，会出现什么

  • workspace / conversation / space / context 四套主语并存。
  • connector 一会儿被当数据同步器，一会儿被当 runtime，一会儿又被当产品模块。
  • 不同 Agent runtime 各自携带自己的 skill / hook / loop 模型，主产品失去定义权。
  • AFFiNE、Obsidian、Supermemory 的参考层级被混淆。
  • 长期会形成多个“半核心层”，每一层都在偷偷定义系统主模型。

当前就该启动的治理动作

  1. 冻结术语表：`Space`、`Thread`、`Mount`、`ConnectorBinding`、`ContextPack`、`Runtime Workspace`。
  2. 冻结责任矩阵：每个模块都必须回答“这是不是我的职责”。
  3. 冻结 connector 边界：哪些是 productized，哪些继续在独立项目孵化。
  4. 冻结 runtime 边界：支持多 runtime，但不承诺私有能力完全等价。
  5. 冻结 ingestion / execution / governance 三条链，避免一条链同时做三件事。

治理成功的标志

  • 新增功能时，能先放到明确层级，而不是先实现再补解释。
  • 同一个对象不会在不同模块里被重新命名和重新解释。
  • connector、runtime、context engine 都能并行演进，但不互相抢主语。
  • 任何一个外部参考项目都只能影响某一层，而不是反向统治全局。

6. 多 Runtime 与 Connector 项目边界

长期支持多种 Agent runtime 是合理的，但不能把产品做成“所有 runtime 的私有协议适配层”。同样，connector 也不能既是外部仓库的内部实现细节，又是主产品未定义边界的万能模块。稳定做法是：ContextGo 持有产品级执行契约，connector 项目负责能力孵化与接入控制面。

多 Runtime 的长期原则

  • 支持多 runtime，但不追求所有私有能力完全等价。
  • skill、hook、multi-agent 的产品语义必须由 ContextGo 定义。
  • runtime adapter 负责把稳定契约翻译成具体 runtime 能力，而不是反过来定义产品主模型。
  • 多 agent 的编排定义权在 ContextGo，不是交给某个 runtime 的私有子 agent 协议。

Connector 项目的长期原则

  • sibling ../connector 仓库负责 connector capability incubation 与 connector control plane。
  • 它负责 datasource / profile / runtime / secret 与外部系统接入形态。
  • 主产品负责 productization、Space 归属、审批治理、Context Engine 接线与 UI/remote surface。
  • 一旦 connector 成为产品能力，其稳定 contract 必须先在主产品仓库中被定义。

Connector 不是 snapshot pipeline

  • snapshot 只是 connector 的一种产物，不是 connector 本体。
  • agent-first connector 的 canonical form 更接近 CLI / MCP / API / managed runtime 这样的 execution surface。
  • 进入 Context Engine 的是其中可沉淀、可检索、可抽象的部分。
  • 进入 Execution Runtime 的是其中可调用、可观察、可审批的 action surface。

建议的稳定 contract

  • Runtime contract：Run lifecycle、context injection、tool surface、artifact IO、capability declaration。
  • Connector contract：context outputs、execution capabilities、runtime handles、health/validation、writeback results。
  • 治理约束：approval broker、audit log、scope isolation 由主产品持有。

7. 核心对象模型

产品层对象和引擎层对象必须分开定义。前者负责归属、协作、执行与审批，后者负责沉淀、压缩、检索与组装。Context Engine 服务于 Space，不能反向定义 Space。

产品层对象

  • Space：长期逻辑空间，定义隔离、归属与成员协作边界。
  • Thread：空间内的一条任务线或执行视图。
  • Mount：当前设备上的本地资源挂载点，不是空间身份。
  • ConnectorBinding：外部系统上下文通道的绑定关系。
  • SourceItem：进入空间的标准化外部上下文对象。
  • Artifact：执行生成的一等产物。

引擎层对象

  • SourceRecord：可回溯的原始轨迹记录。
  • DocumentSnapshot：稳定归档的文档快照。
  • Chunk：最小检索单元。
  • MemoryCandidate：待评估、待升级的候选记忆。
  • MemoryEntry：长期有效的高价值语义状态对象。
  • ProfileSegment：多条记忆压缩出的高层规则、画像或元认知片段。
  • ContextPack：一次执行真正发送给 agent 的上下文载荷。

8. 记忆生命周期与索引策略

一个完整的 memory system 不是“向量库 + 若干 prompt”，而是一套会形成、升级、压缩、遗忘、审查和再装配的运行机制。不同记忆层应采用不同存储与索引结构。

生命周期闭环

  1. Formation：从聊天、编辑、connector、文件、Agent 产物生成候选记忆。
  2. Promotion：把候选提升为长期记忆，自动或人工确认。
  3. Compaction：将多条记忆压缩成 profile、规则或更高层抽象。
  4. Forgetting：降权、归档、软删除、冲突替换，而不是简单丢弃。
  5. Review：对高影响约束、团队规则和长期事实执行人工审阅。
  6. Assembly：按任务范围、token 预算和优先级组装 Context Pack。

多层索引策略

  • Lexical Index：关键词、精确字段、命名实体过滤。
  • Vector Index：语义近邻和 chunk / doc 召回。
  • Structured Index：偏好、约束、决策、身份等 typed memory。
  • Graph Edges：supports / updates / derives / contradicts / belongs_to。
  • Temporal Index：recency、活跃 thread、最近变化。
  • Scope Index：space / thread / connector / source kind / member 范围过滤。

9. AFFiNE 的正确吸收方式

AFFiNE 的价值在于 local-first、doc/canvas 融合、块级内容模型、协同存储与人类友好的工作台交互。要吸收的是这些能力，而不是把 AFFiNE 当成外围 provider 或直接让它定义 ContextGo 的顶层产品边界。

应当吸收的能力

  • doc + canvas 的统一工作表面。
  • block-based 内容模型和 edgeless interaction。
  • local-first storage / sync / collaboration substrate。
  • 让人更容易编辑、组织、审阅上下文的交互模式。

不应交给 AFFiNE 定义的部分

  • Space 的产品级身份与命名。
  • Agent runtime、connector orchestration、IM channel 模型。
  • memory lifecycle、context governance、approval 规则。
  • Context Pack 的装配逻辑和执行时决策权。
不是 AFFiNE as provider，而是 AFFiNE capability absorption into ContextGo Space。

吸收后的定位

AFFiNE 更适合作为 Space Surface substrate 与 local-first collaboration substrate 的能力来源，进入 Space Docs、Space Canvas、内容组织与协作表面。

最终边界

ContextGo 继续定义顶层 Space、长期上下文引擎、execution runtime 与 connector / channel 体系；AFFiNE 贡献的是人类表面与内容底座，而不是系统主语。

10. 分阶段实施路线

为避免继续在 workspace / conversation / space / context 四套心智模型中来回漂移，建议先锁边界，再补 ingestion 和 context pack 中枢，最后再做更强的图谱和协作表面。

Phase 0

冻结术语和责任边界。

  • 统一 Space / Thread / Mount / Runtime Workspace / SourceItem / Artifact / ContextPack 的定义。
  • 明确 Conversation 在迁移期只是 Thread 的近似承载。
Phase 1

先做归属和 provenance，再谈高级检索。

  • 长期对象优先补齐 spaceId。
  • 统一 threadId / connectorBindingId / mountId / origin 等追踪字段。
Phase 2

统一 ingestion 入口。

  • connector、工作目录、IM、文档编辑、Agent 产物都走标准入库路径。
  • 不允许每类来源各自发明独立 memory 写法。
Phase 3

把 Context Pack 组装做成系统中枢。

  • 区分 thread state、active space context、retrieved memory、profile、evidence、runtime context。
  • 让每次 Agent 执行都可解释、可裁剪、可审查。
Phase 4

补齐记忆生命周期闭环。

  • 上线 promotion、review、compaction、forgetting、profile refresh 的 runtime 闭环。
  • 区分自动升级与人工审批的边界。
Phase 5

再做图谱、Canvas 和更强的人类协作表面。

  • 图谱要服务于解释、审查和导航，而不是先于 engine core 独立膨胀。
  • Space Docs / Space Canvas / Members 才是长期协作的落点。
本报告用于固定 ContextGo 的长期上下文引擎方向：Space-first、Context Engine 独立化、Context Pack 产品化，以及对 AFFiNE 与 Supermemory 的能力吸收边界。它不是代码实现说明，而是下一阶段所有数据模型、UI 表面与 runtime 接线的共同约束。
