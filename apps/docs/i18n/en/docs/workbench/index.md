# Workbench

The primary product object in ContextGo is not one chat page. It is the workbench.

Different kinds of work should be able to live in different workbenches while sharing the same product shell, context layer, and runtime system.

![ContextGo workbench home](/brand/docs/workbench-home.png)

The first thing users should feel is not just a chat box. It should be a workbench home that can host multiple work surfaces, agent capabilities, and context entry points.

![ContextGo workbench space and project entry](/brand/onboarding/create-space.png)

The workbench also owns spaces, project entry points, and default workspace switching rather than only one chat frame.

## Why the product emphasizes workbench

ContextGo is not trying to carry only one-off conversation. It also has to hold:

- long-running sessions and cowork loops
- browser and research work
- file, space, and context governance
- multi-agent, automation, and publication paths

If all of that is compressed into a single chat layout, the product model becomes unstable.

## Keep these three boundaries separate

1. **Workbench is the product work surface**
   It owns entry points, state, and capability distribution for different task types.
2. **Conversation is only one workbench mode**
   It matters, but it should not equal the whole product.
3. **Context, runtimes, and automation are not chat add-ons**
   They are shared system layers beneath the workbench.
