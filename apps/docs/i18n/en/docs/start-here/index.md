# Start Here

This section answers two questions:

- what product model you should hold before reading the rest of the docs
- what order is safest once you are ready to install, connect a runtime, and use remote access

It is not a feature list. It is the starting point for the public documentation set.

![ContextGo product surface overview](/brand/docs/start-here-overview.png)

On a first read, you do not need to understand every detail in the image. You do need to recognize the stable surfaces: the workbench home, connector entry layer, built-in agents, context space, scheduling, and the remote entry point.

## One-sentence definition

The most stable public definition today is:

> ContextGo is a desktop-first Agent Workbench where the desktop host remains the execution authority.

That implies three things:

- the host machine is still where real execution happens
- the product is broader than one chat surface
- its value comes from connecting context, runtimes, remote access, and publication into one system

## Four judgments to lock in first

For a first pass, treat ContextGo as:

1. a work system where the desktop host remains the execution authority
2. a product that organizes files, pages, browser context, docs, and prior results into durable context
3. a workbench that can assemble runtimes, skills, automation, and agent packages
4. a system that can move from local use into remote access and real channel publication

## Who this section is for

Start here if you are:

- brand new to ContextGo and need the product definition first
- preparing to install the desktop app and want the safest order
- already familiar with coding runtimes but want a product model that goes beyond one terminal entry point
- trying to understand remote access, multi-device use, and publication within one system

## What not to do first

Do not begin by:

- connecting many runtimes at once
- designing heavy automation too early
- treating mobile as the primary host surface
- starting from publication before a local workflow works
- trying to understand every feature before one real task loop succeeds

## What counts as a successful start

For most users, the first stage is successful only when all four of these are true:

- one usable desktop host exists
- at least one runtime is truly ready
- real working material entered the system
- one small useful task finished successfully
