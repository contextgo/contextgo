# Context System Overview

ContextGo is not just message history stitched together.

## What this page clarifies

Many products describe "context" in vague terms, but in practice that often means only:

- longer chat history
- more attached files
- pasted summaries of a few pages

That is not the model here.

## Its long-term value comes from a fuller context system built around:

- Context Connector
- Context Engine
- Session / Project / Space
- Memory / Profile / Context Pack

## A stable four-layer view

You can treat the system as four layers.

### 1. Source layer

Pages, files, docs, and external system records enter as sources the system can reference.

### 2. Distillation layer

The system does not just stuff all sources back into every task. It gradually distills higher-value long-term material.

That includes:

- retrievable structured content
- more stable memory
- higher-level profile signals

### 3. Boundary layer

Session, Project, and Space are not the same thing.

They separate:

- the current execution view
- a working unit
- a longer-lived context container

### 4. Assembly layer

What the agent finally receives is a task-specific Context Pack.

It should be selected, shaped, and assembled, not dumped in as raw history.

## Why this layer matters most

Without this layer, the agent keeps restarting from weak context.

With it:

- work becomes more continuous
- project knowledge becomes reusable
- longer-running workflows become possible

## Common misunderstandings

- "Context just means chat history."
- "If I upload enough materials, quality will naturally become high."
- "Memory is just an archive of raw messages."

All three are too shallow.

## What is most useful for users to understand

The most useful user-level questions are:

- how real sources enter the system
- how longer-lived knowledge gets distilled
- what the current task actually receives

Once those are clear, it becomes much easier to judge why one output is well grounded and another is not.
