# Context Engine

Context Engine should not be understood as a hidden memory database sitting behind the product.

Its role is closer to:

- forming context
- distilling context
- compacting context
- assembling context
- helping work continue across sessions

## What it should not do

It should not replace visible project truth.

Project-level truth should remain in surfaces users can inspect, edit, and version.

## What it really does

The engine is better suited for:

- extracting high-value information from work
- promoting stable knowledge into longer context
- preparing better context packs for future turns
- helping session, project, and space context evolve over time

## How it differs from an ordinary memory layer

This is not only about "remembering more."

The bigger difference is that it:

- shapes raw signals into memory, profile, and context packs
- keeps governing context instead of only accumulating history
- reduces the entropy caused by stale constraints, repeated material, and polluted intermediate state

In other words, Context Engine is not just a memory layer. It is a context stabilizer.

## Why it needs a `context space`

Not every durable signal should be attached directly to one physical project.

Some patterns naturally span multiple projects, such as:

- your writing and collaboration preferences
- success and failure patterns for one kind of work
- judgment frameworks reused across projects

That is why ContextGo needs a logical `context space`, not only isolated per-directory memory.

## Why local-first background governance matters

Many high-value signals do not become clear in one turn. They emerge over time while work is happening.

That means Context Engine is well suited to background governance while you are away, such as:

- distilling durable signals
- compacting repeated context
- identifying stale project clues
- preparing a cleaner context pack for the next task
