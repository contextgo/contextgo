# Product Map

如果你把 ContextGo 只理解成一个聊天页，会错过它真正的结构。

更准确的理解方式，是把它看成一组相互配合的产品面，而不是一个单点功能。

## 1. Workbench

这是你真正开始工作的地方。

它负责承接：

- 对话与协作式工作
- 文件、网页、结果的查看与继续
- 与 runtime、上下文和任务流的实际交互

如果把 ContextGo 看成一个产品入口，Workbench 就是入口中的入口。

## 2. Context

这是长期价值层。

它处理的问题不是“这次问了什么”，而是：

- 你的材料来自哪里
- 它们如何被组织成可复用上下文
- 后续任务如何继续利用这些结果

## 3. Agents & Capabilities

这一层回答系统如何获得能力：

- 用哪个 runtime 执行
- 有哪些 Assistant / Agent Package
- skills、hooks、commands、schedules 如何补充能力

它决定的是“系统能做什么”和“这些能力如何被装进去”。

## 4. Remote & Devices

这一层定义主机和客户端的关系：

- 哪台设备是真正执行主机
- 网页端和手机端扮演什么角色
- Linux 在 Host Runtime 模型里如何定位

这是理解多端体验的关键层。

## 5. Publish

这一层让一个已经在本地跑顺的能力进入真实渠道。

它关心的不是单纯“能不能发消息”，而是：

- 通过哪个入口触达
- 面向哪个 audience
- 怎样在多个入口复用同一能力

## 6. Collaboration

这一层把系统从单人单 Agent 工作推进到更复杂协作：

- 多 Agent 协作
- 群组工作流
- harness 风格流程

如果你当前只是单人使用，可以先知道它的存在，不需要第一天就深入。

## 7. Manage

这一层承接稳定运行需要的基础面：

- 账号与设备
- 设置与更新
- 安全与权限
- 故障排查

这是让系统可持续使用而不是“只演示一次”的部分。
