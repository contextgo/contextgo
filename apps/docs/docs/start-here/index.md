# Start Here

这一部分回答两个问题：

- 第一次接触 ContextGo 时，应该先建立什么产品理解
- 已经准备安装、接 runtime、接远程访问时，应该按什么顺序推进

它不是功能清单，也不是营销页补充说明。它是整套公开文档的起点。

## 先用一句话理解它

当前最稳定、最适合对外表达的定义是：

> ContextGo 是一个以桌面主机为执行权威的 desktop-first Agent Workbench。

这句话里有三层意思：

- 真正执行任务的是桌面主机，而不是手机
- 产品重点不是单一聊天页，而是长期工作台
- 价值不只在“问一次答一次”，而在于把上下文、运行时、远程入口和发布链路接成同一个系统

## 先抓住四个核心判断

第一次阅读时，请先记住这四件事：

1. **桌面主机是执行权威**
   文件、本地工具、长任务和大多数运行时能力默认都在主机侧。
2. **网页和手机是远程使用面**
   它们负责接入、查看、继续、上传，不负责替代主机成为长期执行宿主。
3. **ContextGo 是工作系统，不是单一 Agent 包装层**
   它把 runtime、上下文、自动化、远程入口和发布渠道组织到一个产品模型中。
4. **推荐先跑通一条真实任务，再扩展系统边界**
   第一阶段不是追求“全部功能已配置”，而是先形成一个可靠闭环。

## 这套文档适合谁

如果你属于下面任意一类，建议从这里开始：

- 第一次接触 ContextGo，需要先理解它到底是什么产品
- 已经准备安装桌面端，想知道最稳的起步方式
- 已经有 Codex、Claude Code、Gemini 这类 runtime 经验，但不想只停留在单一命令行入口
- 想把远程访问、多端使用、渠道发布放进同一套理解里

## 第一阶段不要做什么

下面这些事都不适合放在第一天：

- 同时接很多 runtime
- 一开始就设计复杂 hooks、commands、schedules
- 先试图把手机端当主入口
- 先把渠道发布当成比本地闭环更重要的目标
- 在还没跑通真实任务前，就开始纠结所有概念是否都已经学完

## 什么叫“已经起步成功”

对大多数用户来说，第一阶段成功不是“功能都看过”，而是下面四件事至少成立：

- 你有一台可用的桌面主机
- 至少一个 runtime 真的 ready
- 你已经把真实材料带进 ContextGo
- 系统已经完成一条有价值的小任务

只要这四件事成立，后面的远程、多端、自动化、发布都可以逐层扩展。
