# Workbench

ContextGo 的产品主对象不是单一会话页，而是工作台。

不同工作类型应该拥有不同工作面，但它们共享同一个外壳、上下文系统和 runtime 能力。

![ContextGo Workbench 首页](/brand/docs/workbench-home.png)

当前最先被用户感知到的，不应该只是一个聊天输入框，而是一个能承载多种工作面、Agent 能力和上下文入口的工作台首页。

## 为什么要强调 workbench

因为 ContextGo 最终承接的，不只是一次性对话，还包括：

- 长期会话与协作
- Browser / research 类型工作
- 文件、Space 和 context 治理
- 多 Agent、自动化和发布链路

如果仍然把所有能力都压缩成一页聊天布局，产品边界会越来越混乱。

## 先把三个边界分开

1. **Workbench 是产品工作面**
   它负责承载不同任务类型的入口、状态和能力分发。
2. **Conversation 只是 workbench 的一种**
   它很重要，但不应该再等于整个产品。
3. **Context、runtime、automation 不是聊天附属物**
   它们应该被视为 workbench 共享的底层系统。
