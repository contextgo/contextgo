# Context

ContextGo 最核心的长期价值，不在单个 Agent，而在上下文系统。

## 这页解决什么问题

如果把 ContextGo 只理解成“一个会话里能调起 Agent”，你会很快遇到瓶颈：

- 每次像从零开始
- 任务之间无法沉淀
- 文件、网页、文档和历史决策无法稳定复用

Context 这部分就是解释 ContextGo 真正长期成立的那一层。

## Context 包含什么

这包括：

- Context Connector
- Context Engine
- Session / Project / Space
- Memory / Profile / Context Pack

## 一个更稳的心智模型

你可以先把它理解成一条链路：

1. 外部资料先通过 Connector 进入系统
2. 系统把资料、历史和结构化信息沉淀下来
3. 检索和组装层从中挑出与当前任务最相关的部分
4. Agent 最终拿到的是整理过的 Context Pack，而不是杂乱原始堆积

所以 Context 的重点，从来不是“存得越多越好”，而是“把该进入当前任务的东西稳定送进去”。

## 为什么它比单次对话更重要

有了这层之后，系统才可能逐步获得：

- 长期连续性
- 跨任务复用
- 更稳定的项目边界
- 更有根据的输出
- 远程和发布场景下的持续一致性

## 对用户最有价值的部分

对普通用户来说，最需要先理解的不是所有内部术语，而是：

- 真实材料怎样进入系统
- 系统怎样区分短期会话和长期上下文
- 为什么高质量输出依赖高质量上下文装配
