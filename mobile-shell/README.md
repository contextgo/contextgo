# ContextGo Mobile Shell

Native shell workspace for running the existing ContextGo WebUI inside mobile apps.

This workspace contains:

- `android/` Android Studio project
- `ios/` Xcode project
- `harmony/` HarmonyOS NEXT / DevEco Studio project
- `shared/` shared notes and assets
- `scripts/` helper scripts

## Product Model

These apps are **native shells** for the existing ContextGo WebUI.

Canonical architecture doc:

- `docs/tech/mobile-remote-control.md`

Canonical command map:

- `docs/tech/mobile-shell-cmd.md`

Canonical release and distribution policy:

- `docs/tech/release-distribution-standards.md`

They do not try to run the Electron main process on mobile. Instead, they:

1. connect to a reachable ContextGo WebUI/server instance
2. load that URL inside a native WebView
3. persist the last successful endpoint locally

The current shells default to `https://remote.contextgo.io/login` on first launch and keep custom host entry as a secondary action for direct or self-hosted access.

In the intended long-term product model:

- desktop is the real execution host
- mobile is the remote use-side / control-side client
- mobile-local files should upload to the desktop host, then be processed there

Accepted connection inputs:

- Base WebUI URL, for example `http://192.168.1.10:3000`
- QR-login URL generated by ContextGo, for example `http://192.168.1.10:3000/qr-login?token=...`

Behavior:

- Base URL is normalized to `/login`
- `/qr-login?token=...` is loaded as-is

## Required Host Runtime

Run ContextGo in one of these modes on a reachable host:

- `bun run webui:prod:remote`
- `bun run server:start:prod:remote`

The mobile shell is only as capable as the WebUI/server runtime. Electron-only bridges remain unavailable on mobile.

## Why This Lives Beside `mobile/`

This repository already contains an Expo-based native client in `mobile/`.

`mobile-shell/` stays separate because:

- it packages the existing WebUI instead of reimplementing screens in React Native
- HarmonyOS requires its own native project structure
- the shell lifecycle, build tooling, and runtime assumptions differ from the Expo app

Keeping both under one repository still gives a single maintenance surface without forcing two different product models into one toolchain.

## Quick Start

1. Start ContextGo WebUI or standalone server on a reachable host.
2. Run `bun run mobile-shell:bootstrap` from the repository root, or `scripts/bootstrap.sh` inside `mobile-shell/`.
3. Open the platform project:
   - Android: `android/` or use `scripts/android-gradlew.sh`
   - iOS: `ios/ContextGo.xcodeproj`
   - HarmonyOS: `harmony/` in DevEco Studio

## Environment Notes

- Android CLI builds expect a compatible JDK, ideally **JDK 17**. Android Studio's bundled JDK is fine.
- iOS CLI builds require the iOS platform runtime/components to be installed in Xcode.
- HarmonyOS builds require DevEco Studio plus the HarmonyOS SDK/tooling.
- The HarmonyOS SDK environment root must point to `~/Library/Huawei/command-line-tools/sdk`, not `~/Library/Huawei/command-line-tools/sdk/default`.
